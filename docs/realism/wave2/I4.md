# I4: progression, entrustment and logbook (plan stream S12)

The game layer is gone. XP, level titles, the day streak, the hint penalty and the 10-hour "obsessive" plan have been replaced by:

- EPA-style entrustment per competency on the EAPCI 2020 levels I to V;
- a simulator logbook that every lab writes to;
- competency-ordered case ladders with a held-out exam pool;
- a real exam mode, with no hints, no coaching and one counted attempt per case;
- three-part module mastery (read, quiz, apply);
- spaced practice of procedural skills alongside the quiz items.

Old local profiles migrate without losing anything. This track also applied the pending shared edits from S13 and S0 that fall in its files. Sources and every model parameter are listed in [../facts/I4.md](../facts/I4.md).

A second round fixed the defects an adversarial review found; see "Review fixes" below.

## Review fixes

| Review item | Severity | Fix |
|---|---|---|
| Final assessment ignored component exams taken on the day level IV was awarded | high | Exam events carry their time `t`. `EntrustmentRecord.awardedAt[4]` holds the time of the exam that completed level IV, and `deriveMaster` accepts component passes with a later `t`. A passed exam later the same day now counts. When only the award date survives (an award carried over from a trimmed logbook), the next day is the first that counts. |
| Fixed exam pool of 3 cases per rung could run out, locking a learner out of levels IV and V | high | Held-out diagnostic cases are now generated on demand from the unbounded X-seed sequence (`examCases` in `catalogue.ts`). Each case's rung comes from the practice rungs' key ranges, and `classifyCase` and `isExamCase` accept any valid X-seed id for the EPA. Level III exams draw only rungs 3-4; level IV exams and the final assessment draw rungs 5-6 (`EXAM_BANDS`). Measured: at least 381 cases per rung within the 6,000-index scan bound. A test runs every component through 7 exams toward III and 10 toward IV (failures, critical errors, abandoned exams), then 3 final-assessment attempts each, to level V, with no case examined twice. |
| Reading exams could be retaken without limit | medium | Each learner's exam-shown items are stored per drill (`seenExamItems`: item, date). Sets come only from items never shown in an exam of that drill (runs, or patients for dominance and planning), with one set per drill per day. Leaving a set logs a failed set, and any failed reading set resets the count toward the next level (`resetsOnFail`). Because the held-out library is small (see Remaining issues), a set may be half a full set (at least 4 items), and items shown more than 90 days ago come back only when unseen items cannot fill a set. The Exam tab shows how many unseen sets remain per drill. |
| Leaving a diagnostic exam logged nothing, so the same seen case came back as a first attempt | medium | A held-out case counts as attempted when it loads (`beginExam`, stored as `pendingExams`). Leaving (button "Leave (counts as failed)"), navigating away (unmount) or closing the app (handled at the next hydrate) logs a failed first attempt (`rowFromAbandonedExam`). Exam selection also excludes pending cases. A finished case closes its pending entry, so a later abandon does nothing. |
| `labPolicy` was not wired into any launch path | medium | The store applies `labPolicy(entrustment[primary EPA]).mode` to every practice session the lab did not label itself: diagnostic `case` and `challenge` runs, and labs that report only a key and a score. Tutorials keep guided and exams keep exam. At level 0-II the session is logged as guided, as assistant; at III as supervised; from IV as independent. `startPractice`, the Case library ladders and the daily challenge also set `activePolicy` (mode, mentor entrustment, `VisibilityPolicy`) in the store for the labs to read. The ladders and the daily challenge show the mode they will log, and the daily challenge's objectives list follows `visibility.recommendedViews`. |
| A first run was described as "converted" | low | `migratedAt` is set only when the stored object held learner data. |
| Reading-exam answers were mixed into practice statistics | low | Exam answers are no longer written to the practice drill results (`saveResults`), so learning curves and module apply credit see practice only. The score is in the logbook row. |
| PCI skill cards were never graded, and the instruction was set as the screen changed | low | Review arms the card on the scenario's sim key (`pci-<scenario>`). The next `recordSim` for that scenario grades it (passed or not). The instruction now stays on Review, with an "Open the PCI lab" button. |
| The daily-cap notice counted failed sessions | low | `passesToday` uses the same rule as `countedRungPasses`. |
| Home and Review read the drill results once per mount | low | Both re-read them whenever the profile changes. |

### The rules in one place

- **Levels.**
  - I: a logged session, or 60% of the linked quiz items retained.
  - II: 3 passed practice sessions on distinct cases.
  - III: 2 exam passes on held-out cases at rung 3 or above, over at least 2 days.
  - IV: 3 more exam passes at rung 5 or above, over at least 2 days.
  - V: level IV plus the final assessment.
- **Critical errors.** A critical-error exam resets the count toward the next level. For reading exams, which have no critical errors, any failed set resets it.
- **Exam credit.** Only the first exam attempt on a case counts. A case counts as attempted when it loads, and leaving before the end is a failed attempt. An exam-mode run on a case outside the pool is logged as independent practice.
- **Exam pool.** Diagnostic held-out cases are generated on demand and never run out. Level III exams use rungs 3-4; level IV and the final assessment use rungs 5-6. Reading exams use unseen held-out items, one set per drill per day, with a 90-day washout only when unseen items run out.
- **Expiry.** Each EPA has an expiry period (60, 90 or 120 days). Without a pass in that period, the level in force drops by one and a refresher is due; awards are kept.
- **Ladders.**
  - Two distinct passes at a rung or above clear it.
  - Only 4 passes a day per EPA count toward the ladder.
  - Cleared rungs feed interleaved review.
  - The daily challenge is the next rung of the weakest due EPA.
- **What the level drives.** `labPolicy(rec, exam)` gives the mode (guided up to II, supervised at III, independent from IV, exam on request), the mentor entrustment 1-5 and `visibilityFor(mode, entrustment)`. The logbook applies its mode and role to every practice session the lab did not label. Launches from the progression screens put the full policy in `activePolicy`, but the labs do not read it yet (integration steps 1 and 10).
- **Final assessment.** One rung 5+ exam pass in each of radial access, left engagement, right engagement, full study and reading. Each must be taken after the exam that completed that EPA's level IV (by time, so later the same day counts), all within 14 days, with no critical-error component exam (or failed reading set) in the window. This defines the critique's undefined "Level 10 Master Assessment". `recordExam("master-assessment")` and `epa:<id>` exam results are written.

## Performance

None of this is on the image path. There is no WebGL and no per-frame work, so the 15 frames/s at 768 x 768 budget is unchanged and GPU cost is 0. CPU costs measured in Node on this Mac:

- **Building all 12 laddered EPAs:** 22 ms in round 1, once, lazily, on first use. In round 2, under `vite-node`, the five diagnostic ladders with their exam display lists took 7.2 ms.
- **On-demand exam cases (round 2):** 200 rung 5-6 cases in 1.4-3.6 ms cold per EPA. A pick after 150 used cases takes 0.02-0.14 ms warm. It runs on a button press, never per frame.
- **`deriveAll` on a 2,000-row logbook:** 4.3 ms in round 1; 3.4 ms in round 2 with 200 exam rows resolved through the on-demand classifier, which caches each id. It runs once per logbook write, not per frame.
- **Three-part mastery for all 68 modules on 2,000 rows:** 6.7 ms per render of Dashboard, Pathway or Review.
- **The store's write path:** one localStorage write per finished session, as before.
